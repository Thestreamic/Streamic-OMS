MNC Software Appoints Heartland Video Systems as North American Reseller, Strengthening Momentum for Tapestry Orchestration Platform

MNC Software Appoints Heartland Video Systems as North American Reseller, Strengthening Momentum for Tapestry Orchestration Platform

The Streamic Editorial Team March 25, 2026 865 words · 4 min read

Orchestration Platforms: From Niche MAM Add-on to Core Workflow Engine

The recent announcement of a new reseller for MNC Software's Tapestry platform signals a broader industry trend: the maturation of orchestration software from a specialized tool within a Media Asset Management (MAM) system to a foundational element for complex broadcast and content delivery workflows. This shift is driven by the need to automate increasingly intricate processes, from ingest and QC to multi-platform distribution, especially as facilities grapple with rising operational costs and the demand for faster content turnaround.

Technical Deep Dive

MNC Tapestry, like other modern orchestration platforms, operates by abstracting underlying infrastructure and services through APIs. It leverages microservices architecture, often deployed within Kubernetes clusters, to manage discrete tasks. For ingest, this could mean interacting with ST 2110 sources via NMOS for discovery and control, then directing streams to transcode engines like Telestream Vantage or Harmonic's VOS360. The platform's strength lies in its ability to chain these API calls, creating automated workflows that can handle conditional logic, error handling, and metadata propagation. This contrasts with older, monolithic MAM systems where workflow automation was often tightly coupled to the storage layer or required custom scripting against proprietary APIs. The dependency shifts from direct storage interaction to API orchestration across a distributed, potentially cloud-native, infrastructure.

Why This Matters in 2026

For regional broadcasters and national PSBs, this means significantly reduced operational overhead. Imagine a workflow where a live sports feed ingested via ST 2110 is automatically transcoded, QC'd for specific broadcast standards (e.g., loudness, aspect ratio), and then prepared for both linear playout and VOD delivery to an OTT platform. This entire chain, previously requiring multiple operator interventions and manual checks, can now be managed by Tapestry, potentially reducing the need for dedicated ingest operators and QC personnel. The CapEx shift is also notable, as these platforms enable better utilization of existing hardware and cloud resources, delaying or reducing the need for new capital expenditure on specialized ingest or automation hardware.
  • For broadcast engineers: This requires a deep understanding of API integration and potentially container orchestration. Engineers will need to configure NMOS endpoints for ST 2110 sources, define API call sequences within Tapestry, and set up monitoring for the orchestration engine itself, not just individual hardware components.
  • For OTT and streaming platforms: The impact is primarily on origin infrastructure and content preparation. Automated QC and metadata enrichment driven by orchestration can ensure ABR ladders are consistently generated with correct tags, reducing manual errors that lead to playback issues or missed monetization opportunities. It also streamlines the process of preparing content for dynamic ad insertion (SSAI).
  • For MAM and post-production teams: Ingest pipelines become more intelligent. Instead of simply dropping files into a watch folder, content can be automatically categorized, tagged with metadata extracted from the ingest stream (e.g., camera angles, timestamps), and routed to specific post-production workflows or archive tiers based on predefined rules, eliminating manual QC steps and accelerating content availability.

Limitations & Engineering Risks

  • Latency and timing constraints: While Tapestry itself is an orchestration layer and not a real-time signal path, the systems it controls can have strict timing requirements. If controlling ST 2110 ingest or playout, maintaining PTP synchronization across all devices managed by the orchestration layer is critical. Jitter exceeding 1 microsecond on the PTP path can cause ST 2110 stream disruptions, impacting the very content the orchestration is meant to manage.
  • Vendor lock-in exposure: While the underlying protocols like ST 2110 and APIs are often standardized, the specific implementation and orchestration logic within Tapestry can create a dependency. Switching to a different orchestration platform would require re-engineering these complex workflows, potentially incurring significant development costs.
  • Integration complexity: Connecting Tapestry to disparate systems, especially legacy equipment lacking modern APIs or robust NMOS support, presents a significant challenge. For instance, integrating with older EVS XS-VIA replay systems might require custom middleware or relying on less granular control mechanisms, leading to brittle workflows that fail unpredictably.
  • Skills and operational gap: Broadcast engineering teams often lack deep expertise in microservices, Kubernetes, and advanced API programming. Deploying and managing an orchestration platform effectively requires upskilling in these areas, which can be a significant hurdle for established operational teams.

Implementation Checklist

  1. Validate the platform's API documentation and test its ability to control a representative set of target systems (e.g., a transcode engine, a MAM ingest API, a cloud storage gateway) in a lab environment.
  2. Verify compliance with relevant standards for the specific workflow components being orchestrated. For ST 2110 ingest, this means ensuring the controlled ingest device adheres to SMPTE ST 2110-20 (RTP payload) and ST 2110-30 (audio payload), and that NMOS IS-04/05 registration and control are correctly implemented.
  3. Ensure the underlying infrastructure meets the platform's requirements. If deploying on Kubernetes, confirm adequate cluster resources, network configuration for inter-service communication, and robust storage provisioning.
  4. Establish comprehensive monitoring for the orchestration engine itself, tracking API call success/failure rates, workflow execution times, and resource utilization of managed services.
  5. Track the roadmap for key standards relevant to the integrated systems. For example, monitor the evolution of JPEG XS for mezzanine contribution and its potential integration into orchestration workflows.
